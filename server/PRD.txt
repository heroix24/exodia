🧾 PRD — Exodia

(Hackathon-optimized edition)

🟣 TL;DR

Exodia turns any Excel file into a fully functional web-based CRUD dashboard — automatically generated by AI. The system parses Excel columns, generates UI code using React + Next.js, creates a GitHub repo using a PAT, pushes the generated components into it, and dynamically loads the code in the frontend. The backend uses Node.js + Hono.js written in plain JavaScript (no TypeScript) to perform real-time CRUD operations directly on the original Excel file stored locally.

This allows non-technical users who treat Excel like a database to finally get:
✔ Automated CRUD
✔ Dashboards
✔ Charts
✔ Real-time edits
✔ And a shareable GitHub repo with generated code

🟣 Problem Statement

Many business users rely on Excel as an accidental “database.” They manually update all values, perform manual totals/calculations, and lack any knowledge of Excel scripting or automation. This makes operations slow, error-prone, and limited.

They need an effortless way to:

Automate CRUD
View data meaningfully (tables, charts, insights)
Use structured interfaces instead of raw cells
Avoid writing formulas or scripts
Manage data across multiple sheets easily
Exodia solves this by reverse-engineering the process of CRUD automation for Excel and generating a complete UI for them instantly.

🟣 User Experience (Step-by-Step)

1. User uploads Excel

On the dashboard, the user drags an Excel file.
Backend parses sheets + headers + column types.
Backend stores the Excel locally:
/uploads/{userId}/{excelId}.xlsx

2. AI generates frontend code

AI receives:

Column name
Sheet structures
Target stack (React + Next.js)

AI generates:

Dashboard.jsx
components/Table.jsx
components/Form.jsx
components/Charts.jsx
metadata.json (schema + UI config)

3. Exodia auto-creates GitHub repo

Using PAT:

exodia-{userId}-{excelId}

Push files:

/Dashboard.jsx
/components/*
/metadata.json
/README.md
(optional) /copy_of_excel.xlsx

4. User sees their newly generated dashboard

Next.js fetches raw code from GitHub:
https://raw.githubusercontent.com/<owner>/<repo>/main/Dashboard.jsx


Dashboard loads:

Data table for each sheet
Create / Update forms
Delete buttons
Auto-generated charts

5. User performs CRUD

Every action hits backend API:

POST /row
PUT /row/:id
DELETE /row/:id
GET /sheet

Backend rewrites the actual Excel file on disk.

6. User can revisit dashboard later

Repo list page shows:

Excel name
Repo link
“Open Dashboard” button

🟣 Technical Considerations

1. GitHub Integration

Use system PAT stored in environment variable.
Repo naming: exodia-{userId}-{excelId}.
Default branch: main.
Push generated code as initial commit.
Expose GitHub repo URL in UI.

2. Excel Handling

Store locally under /uploads.
Use library like xlsx for CRUD.
Validate column types before generating UI.

3. Dynamic Code Loading

Next.js:

Fetch raw Dashboard.jsx via GitHub.
Compile/evaluate in browser using dynamic imports.
Use fallback UI if fetch fails.

4. Backend

Hono.js for API routing.
Plain JavaScript (ES modules) implementation — no TypeScript.
JWT auth.
AI code generation endpoint.
CRUD operations write to Excel.
Use DTO-style request/response payloads to keep API contracts explicit.
Adhere to SOLID and KISS principles so backend modules stay simple to extend.
Organize backend into router, service, CRUD/repository, schema validation, and model layers for clarity.

5. Database Infrastructure

Run PostgreSQL through Docker Compose using the `pgvector/pgvector:pg18-trixie` image so vector operations are available for future AI features.
Mount a volume for data durability and expose the container via an internal network only accessible to the backend.
Inject the container connection string through environment variables so the backend can coordinate Excel metadata with the Postgres datastore.

6. OpenAPI Contract & DX

Publish an OpenAPI 3.1 spec (`server/openapi/exodia.yaml`) that covers every CRUD and auth route. Keep the spec as the single source of truth by tagging controllers/services with schema decorators or by running a build-time generator so the YAML never drifts from reality. Expose interactive docs (Swagger UI or Redoc) at `/docs` for judges, and generate typed SDKs (frontend + testing helpers) directly from the spec to reduce manual wiring.
